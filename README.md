# Telegram Codex Bridge

PC에서 시작한 Codex 작업을 Telegram으로 확인하고, 필요한 승인과 답변을 보낼 수
있는 개인용 브리지입니다.

## 평소 사용 흐름

1. `start.cmd`로 브리지를 실행합니다.
2. Telegram에 작업을 보내거나 PC에서 `codex-tg.cmd "테스트하고 오류를 수정해줘"`를 실행합니다.
3. `/status`로 경과 시간, 명령 실행·파일 수정 등 현재 활동, 승인·질문 대기를 확인합니다.
4. 승인 버튼을 누르거나 질문에 답합니다. 작업 중 일반 메시지는 추가 지시로 전달됩니다.
5. 완료 알림을 놓쳤다면 `/last`로 최근 결과를 다시 확인합니다. 중단하려면 `/cancel`을 보냅니다.

결과는 휴대폰에 맞는 짧은 발췌로 표시하며 `[📄 전체 원문]` 버튼 또는 `/detail`로 전체
UTF-8 텍스트 파일을 받을 수 있습니다. 자동 요약이 아니므로 전체 문맥은 원문에서 확인하세요.
`Codex 응답 완료`는 응답이 끝났다는 뜻이며, 작업의 모든 요구사항이 성공했다는 판정은 아닙니다.

## 응답이 없거나 요청을 놓쳤을 때

| 보이는 상황 | 할 일 |
|---|---|
| 승인 버튼이나 질문을 찾기 어려움 | `/pending`으로 다시 받기 |
| 연결 끊김 또는 접수 여부 확인 필요 | 같은 작업을 다시 보내기 전에 `/reconnect` 실행 |
| PC 명령을 보냈는데 접수됐는지 모름 | `codex-tg.cmd --status` 또는 표시된 접수 번호로 조회 |
| 완료 메시지를 놓침 | `/last`로 최근 결과 보기 |
| 결과의 전체 내용이 필요함 | 결과의 `전체 원문` 버튼 또는 `/detail` |
| 민감한 입력 차단 안내 | PC에서 값을 설정한 뒤 `/cancel`, `/new`로 새 대화 시작 |

`/reconnect`는 Codex 연결을 재설정하므로 진행 중 작업이 중단될 수 있습니다.
사용하던 대화의 최근 작업 상태를 확인하며 이전 요청을 자동으로 실행하지 않습니다.
아직 작업을 한 번도 보내지 않은 빈 대화는 새로 준비합니다.
연결 복구에 실패하면 새 작업 접수를 막고 PC에서 확인할 내용을 안내합니다.

`/last`는 완료·실패·중단 결과 중 가장 최근 1건을 브리지 메모리에 보관합니다.
새 대화(`/new`)를 만들어도 조회할 수 있지만, 브리지를 재시작하면 지워집니다.
진행 상황은 `/status`를 보냈을 때 조회하며, 주기적인 알림을 자동 전송하지 않습니다.

## PC에서 작업을 시작하고 Telegram에서 승인하기

브리지가 실행 중일 때 이 폴더의 `codex-tg.cmd`로 작업을 시작합니다.

```powershell
.\codex-tg.cmd "프로젝트 테스트하고 오류를 수정해줘"
```

이 명령은 별도 Codex CLI를 실행하지 않고, `127.0.0.1`에만 열린 인증된 로컬
제어 통로를 통해 현재 Telegram 브리지의 Codex 세션으로 작업을 보냅니다. 명령
실행, 파일 변경, 추가 권한, 사용자 선택이 필요하면 Telegram에서 일회용 버튼으로
결정하고 결과도 Telegram에서 받습니다.

PC 명령은 브리지가 요청을 받으면 접수 번호를 바로 표시합니다. Codex가 실제로
받았는지는 다음 명령으로 확인할 수 있습니다.

```powershell
.\codex-tg.cmd --status
.\codex-tg.cmd --status <접수-번호>
.\codex-tg.cmd --help
```

`--status`는 접수 여부를 확인하는 명령입니다. 실행 진행 상황과 최종 결과는 Telegram의
`/status`, `/last`에서 확인합니다. 통신 응답을 놓치면 PC 명령은 동일한 접수 번호로
한 번만 재확인하므로 같은 작업을 새로 실행하지 않습니다.
접수 기록은 현재 브리지 실행 중 최대 1,000건을 메모리에 보관합니다. 재시작 후에는
기록이 사라집니다. 자동 재확인 중 재시작이 감지되면 이전 실행의 요청을 거절합니다. 이전 접수 번호가 조회되지
않으면 Telegram에서 상태를 먼저 확인하세요. 새 명령으로 같은 문장을 보내면 새 요청입니다.

브리지 메시지에는 프로젝트명과 `원격 제어` 표시가 붙고, 작업이 정해지면 짧은 작업
번호도 표시됩니다. 전체 작업 경로와 권한은 `/where`로 확인합니다.

Telegram의 답장 기능을 쓸 때는 현재 작업에 연결된 메시지만 입력 대상으로 받습니다.
다른 PC 세션의 알림, 이전 작업, 재시작 전 메시지에 답장하면 전달하지 않고 확인 방법을
안내합니다. 답장 없이 보내는 일반 메시지는 현재 브리지 프로젝트로 전달됩니다.
사진·문서·음성 입력은 아직 지원하지 않으며 텍스트로 설명하도록 안내합니다.

일반 `codex` 또는 Codex 앱으로 직접 시작한 독립 세션은 이 승인 경로를 사용하지
않습니다. 원격 승인이 필요한 PC 작업은 `codex-tg.cmd`로 시작해야 합니다.

Telegram을 내 PC의 Codex `app-server`에 연결하는 개인용 브리지입니다.

- Telegram 메시지로 Codex 작업 시작
- 진행 중인 작업에 추가 지시 전달
- 명령 실행·파일 변경·추가 권한을 Telegram 버튼으로 승인 또는 거부
- Codex의 선택형·주관식 질문을 Telegram에서 답변
- 작업 완료·실패·중단 결과 수신
- 외부 포트를 열지 않는 Telegram long polling
- 하나의 `ALLOWED_CHAT_ID`만 허용
- 같은 봇 설정의 중복 실행을 시작 단계에서 자동 차단

## 요구 사항

- Node.js 20 이상
- 설치 및 로그인된 Codex CLI
- Telegram `@BotFather`가 발급한 봇 토큰
- PC 전역 완료 알림 및 전체 테스트: Python 3.10 이상 (`python` 또는 테스트의 `PYTHON` 환경변수)

현재 PC에서는 PowerShell 실행 정책 때문에 `codex` 대신 `codex.cmd`를 사용합니다.

## 1. Telegram 봇 만들기

1. Telegram에서 `@BotFather`를 엽니다.
2. `/newbot`을 실행하고 봇 이름과 username을 정합니다.
3. 발급된 토큰을 안전하게 보관합니다.
4. 만든 봇과 대화를 열고 `/start`를 한 번 보냅니다.

## 2. 설정

`.env.example`을 `.env`로 복사합니다.

```powershell
Copy-Item .env.example .env
notepad .env
```

먼저 `TELEGRAM_BOT_TOKEN`만 입력한 뒤 chat ID를 확인합니다.

```powershell
npm.cmd run discover:chat-id
```

출력된 숫자를 `ALLOWED_CHAT_ID`에 넣고, Codex가 작업할 절대 경로를
`CODEX_WORKDIR`에 넣습니다.

```env
TELEGRAM_BOT_TOKEN=123456789:실제_토큰
ALLOWED_CHAT_ID=123456789
CODEX_WORKDIR=C:\projects\my-project
```

`.env`와 `.state.json`은 Git에서 제외됩니다.

## 3. 점검 및 실행

```powershell
npm.cmd run check
npm.cmd test
npm.cmd run smoke:app-server
start.cmd
```

실행 후 Telegram에서 `/help`를 보냅니다.

## Telegram 명령

- 일반 메시지: 새 Codex 작업을 시작하거나 진행 중인 작업에 추가 지시
- `/status`: 현재 활동, 경과 시간, 승인·질문 대기 상태
- `/last`: 최근 완료·실패·중단 결과와 소요 시간 다시 보기
- `/detail`: 최근 결과의 전체 원문을 텍스트 파일로 받기
- `/pending`: 아직 해결되지 않은 승인 버튼과 현재 질문 다시 받기
- `/reconnect`: Codex 연결 재설정 및 기존 대화 복구 (작업이 중단될 수 있음)
- `/new`: 새 Codex 스레드 생성
- `/cancel`: 진행 중인 turn 중단
- `/where`: 작업 경로와 권한 설정 확인
- `/help`: 도움말

## 보안 기본값

- Sandbox는 `workspace-write` 또는 `read-only`만 허용합니다.
- 승인 정책 `never`와 Sandbox `danger-full-access`는 설정 단계에서 거부합니다.
- 세션 전체 승인은 Telegram UI에 제공하지 않습니다.
- 추가 권한은 요청받은 범위 그대로 이번 turn에만 허용합니다.
- 승인 callback은 한 번 처리된 후 만료됩니다.
- 재전송된 승인 버튼도 같은 요청에 대한 결정은 한 번만 전달합니다.
- 비밀 입력으로 표시된 질문은 Telegram으로 보내기 전에 거절합니다. 새 대화를 시작하기
  전까지 일반 텍스트 입력도 차단합니다. 봇이 임의의 메시지에서 모든 비밀을 탐지하는 것은 아닙니다.
- 허용된 개인 chat ID 외의 메시지는 무시합니다.
- 같은 Bot 토큰과 chat ID로 이미 실행 중이면 두 번째 프로세스는 Telegram 연결 전에 종료됩니다.

Telegram 봇 채팅은 종단간 암호화가 아닙니다. API 키, 비밀번호, 복구 코드와
같은 비밀정보를 Codex 질문에 답변하는 방식으로 전송하지 마세요.

## 운영 참고

- PC가 켜져 있고 `start.cmd`가 실행 중이어야 합니다.
- 동시에 터미널 TUI와 Telegram에서 같은 스레드를 조작하지 않는 것을 권장합니다.
- 브리지가 마지막 `threadId`를 `.state.json`에 저장하고 다음 실행 때 재개합니다.
- `codex app-server`를 인터넷에 직접 노출하지 않습니다.
- PC와 Telegram 입력이 겹치면 도착한 순서대로 처리합니다. 작업 하나를 시작하고
  나머지 메시지는 그 작업에 추가 지시로 전달합니다. 별도 작업 대기열은 아닙니다.
- 작업 접수 알림이 늦거나 실패해도 접수된 작업은 계속됩니다. 다시 보내기 전에
  `/status`를 확인하세요. 완료 알림 전송 실패는 `/last`로 확인할 수 있습니다.
- 코드 업데이트는 실행 중 작업이 끝난 뒤 기존 브리지를 종료하고 `start.cmd`로
  다시 실행하면 적용됩니다. 두 번째 브리지를 먼저 띄우면 중복 실행 차단이 동작합니다.
- Codex 통신 응답은 30초, 일반 Telegram 요청은 시도당 10초 안에 응답을 기다립니다.
  이는 통신 응답 제한이며 Codex 작업 자체의 최대 실행 시간은 아닙니다.
- 승인·질문은 일시적인 통신 오류에 한해 최대 2회 추가 전송합니다. 메시지가 중복 표시될
  수 있지만 승인 결정은 중복 처리하지 않습니다. 계속 실패하면 `/pending`을 사용하세요.

## 코드 구조와 검증

흐름은 `src/index.mjs` → `src/bridge.mjs` → `src/app-server-client.mjs`입니다.
Telegram 통신은 `src/telegram-client.mjs`, PC 입력은 `src/local-control.mjs`,
메시지 표현은 `src/format.mjs`에서 담당합니다. 새 기능을 읽을 때는 bridge의
입력 처리, 상태 조회, Codex 알림 처리 순서로 살펴보면 됩니다.

결과 미리보기는 `src/result-presentation.mjs`, PC 알림 전달·중복 억제는
`src/notification-delivery.mjs`에서 담당합니다. 기존 Python 알림 진입점은 argv 계약을
유지하면서 UTF-8 stdin으로 `scripts/notify.mjs`를 실행하여 같은 표시·통신 코드를 사용합니다.

`npm.cmd test`는 실제 Telegram 메시지나 Codex 작업을 보내지 않고 상태 전이,
동시 입력, 알림 실패, 승인·질문 처리를 검증합니다. `npm.cmd run smoke:app-server`는
실제 Codex 연결과 읽기 전용 임시 스레드 생성을 확인하며 모델 작업은 실행하지 않습니다.
`npm.cmd run smoke:app-server -- --recovery`는 별도의 검증용 대화에 합성 이력을
넣어 조회·연결 종료·재시작·재개를 확인하고 대화를 보관 처리합니다. 모델 작업이나
Telegram 전송은 실행하지 않습니다.
현재 작업·검증 결과는 `STATUS.md`와 `tasks/`에 있습니다. 기존 설치본의
`STOT.md`는 로컬 운영 이력이며 개인 환경 정보가 포함되어 GitHub에서 제외합니다.

알림 통합 테스트는 임시 설치본에서 실제 Python/Node 자식 프로세스를 실행하고 HTTP만
가짜 응답으로 바꿉니다. 실제 봇 메시지나 사용자 대화 원문은 사용하지 않습니다.

## PC에서 직접 시작한 Codex 작업 알림

Telegram에서 시작한 작업은 승인·질문·완료를 모두 봇에서 처리합니다. 별도의
Codex CLI에서 직접 시작한 작업도 전역 `notify` hook을 설정하면 완료 결과를
Telegram으로 받을 수 있습니다. 현재 공식 `notify` 이벤트는
`agent-turn-complete`만 지원하므로 직접 시작한 CLI 작업의 승인과 질문은 해당
터미널에서 처리해야 합니다.

이 경로의 기본 표시는 `📩 PC 응답 도착`입니다. 프로젝트명·작업 번호와 `알림 전용`을
명시하며 이 알림에 답장해도 해당 PC 세션을 원격 제어하지 않습니다.
짧은 일반 답변은 메시지 하나, 긴 결과는 발췌와 전체 원문 텍스트 파일로 전달됩니다.
제목 또는 요약 단일 필드 JSON은 소리 없는 참고 알림으로 표시하고 원본 JSON도 파일로
보존합니다. 내부 보조 응답인지 확정할 정보가 없으므로 이를 임의 삭제하지 않습니다.
일반 JSON 결과는 그대로 처리합니다.

원문 파일은 이미 전달 대상인 응답 텍스트로 메모리에서 생성합니다. 응답에 적힌 임의의
PC 파일을 읽거나 업로드하지 않으며, PC 경로와 파일 인용 표식은 미리보기에서 PC 확인 대상으로
안내합니다. 실제 PDF·이미지 등 산출물 전송은 이 기능의 범위에 포함되지 않습니다.

`.notify-dedup/`에는 전송을 시도한 이벤트의 해시와 시간만 저장합니다. 봇·채팅·작업 경로·
스레드·턴이 같은 이벤트의 반복 시도를 막으며, 최근 24시간 이내 최대 1,000건만 유지합니다.
동시 프로세스는 디스크 처리 동안만 짧은 loopback 잠금을 공유합니다. 전송 여부를 확인하지
못한 이벤트도 자동 재전송하지 않으므로 PC의 원래 Codex 대화에서 확인하세요. 보관 범위를
벗어났거나 이벤트 ID가 없으면 중복 방지를 보장하지 않습니다. 응답 본문·경로·토큰은 이 기록에
저장하지 않으며 Git에서도 제외합니다. PC 작업의 실행 접수 기록과는 별개의 알림 기록입니다.
